# 第二阶段实施与验收基线

本阶段由用户明确授权，沿用第一阶段 LocalService、单数据库连接、受限 IPC、事务迁移及 revision 事件。保留 migration 0001 的原始内容，不重建用户库。

## 业务规则与接口

- 收集箱：未删除、未完成、planned_date 为空。今天：未完成且 planned_date≤用户本地今天；过去日期标注计划逾期。计划：未完成且 planned_date>今天。已完成：未删除且 status=completed。截止逾期独立标注，不把没有计划日期的任务移出收集箱。
- 已删除任务从四视图排除，可从已删除列表恢复。恢复保留原状态及完成时间。
- 截止分为无截止、纯日期 due_date、时间点 due_at 三种，后两者互斥。纯日期始终按 YYYY-MM-DD 处理，精确时间转为 UTC；本地跨天或时区变化后重新计算视图。
- 子任务在任务聚合中编辑、排序、删除和切换完成，和父任务版本、审计一起提交。进度从子任务状态计算。全部子任务完成不会自动完成父任务；父任务有未完成子任务时需再次确认。
- task.version / category.version 实现乐观并发控制。过期写入返回 CONFLICT，保留编辑草稿，要求重新载入。写入失败不更新为“已保存”。
- 分类删除将任务分类清空并递增这些任务版本，保留任务、子任务及操作审计。

## 数据与同步

Schema 2 新建 categories、tasks、subtasks、task_history、task_state。任务状态、日期、外键、截止互斥、完成时间、UUID 和排序字段有数据库约束，Rust 再做严格校验。审计保存任务聚合前后快照，为第五阶段历史浏览预留基础。

事件 taskdock://tasks-changed 仅携带已提交 revision。前端先订阅后读取、合并连续刷新、忽略旧响应；窗口获焦、手动刷新和日期变化时补读。设置同步不改变。浏览器预览保留内存设置，任务操作明确要求桌面版，不建立第二个任务真相源。

按窗口最小授权：三个窗口读任务；main 编辑任务/分类及恢复；quick-entry 只创建任务；widget 只切换完成状态。继续禁止 SQL/fs/shell/远程来源及前端事件发送。

## 实施顺序

1. 新迁移、日期/类型契约、Rust 任务仓储/业务事务和边界测试。
2. LocalService 与 IPC、Pinia 任务同步、视图/日期工具。
3. 四视图、真实详情抽屉、分类与子任务编辑、已删除恢复、小组件和快速添加。
4. 交互测试、原有测试回归、类型/格式/Clippy/release、可执行的 Windows 原生检查。
5. 更新 README、数据模型与测试文档，提交 stage-2-report.md 后停止。

不实现第三阶段及以后模块。迁移的失败回滚必须保留现有库；额外下行 SQL 仅允许空业务库回退，禁止通过回退脚本删除已有任务数据。
